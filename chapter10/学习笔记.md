## 一、为什么要学这章？

### 第7章 ReAct Agent 的三个根本限制

第7章我们构建的智能体已经能推理 + 调工具了，但它有三个天花板：

| 限制 | 表现 | 类比 |
|------|------|------|
| 工具集成困境 | 每接入一个新服务（GitHub/数据库/文件系统）都要手写一个 Tool 类，不同开发者写的工具互不兼容 | 每种电器都要专属插座 |
| 能力扩展瓶颈 | 能力被锁死在预先定义的工具集里，运行时无法发现新服务 | 手机不能插新卡 |
| 协作的缺失 | 多智能体协作（研究员+撰写员+编辑）只能手动编排 | 没有电话的团队只能靠人传话 |

**通信协议的核心价值**：提供标准化接口规范，让智能体用统一方式访问各种外部服务，无需为每个服务写适配器。就像 TCP/IP 让不同设备互通，通信协议让智能体、工具、服务互通。

### 三个协议各解决什么问题

| 协议 | 提出方 | 解决什么 | 一句话类比 |
|------|--------|----------|-----------|
| **MCP** (Model Context Protocol) | Anthropic | 智能体 ↔ 工具/资源的标准化通信 | 智能体的 USB-C |
| **A2A** (Agent-to-Agent Protocol) | Google | 智能体 ↔ 智能体 点对点协作 | 智能体之间的对话 |
| **ANP** (Agent Network Protocol) | 开源社区 | 大规模智能体网络的发现/路由 | 智能体的"互联网" |

**选型指南**：
- 智能体要访问外部服务（文件、数据库、API）→ **MCP**
- 多个智能体相互协作完成任务 → **A2A**
- 构建大规模智能体生态 → **ANP**

## 二、MCP 协议实战（智能体的 USB-C）

### 2.1 MCP 架构：Host / Client / Server 三层

```
  用户提问
     │
     ▼
┌─────────────────────┐
│  Host（宿主层）      │  Claude Desktop：接收提问、管理对话流程
│  内置 MCP Client     │
└─────────┬───────────┘
          │ 需要访问文件系统时激活
          ▼
┌─────────────────────┐
│  Client（客户端层）  │  与 Server 建立连接、发请求、收响应
└─────────┬───────────┘
          ▼
┌─────────────────────┐
│  Server（服务器层）  │  执行实际操作（扫描文件、查库、搜代码）
└─────────────────────┘
```

**关注点分离**：Host 管用户体验，Client 管协议通信，Server 管具体功能。开发者只需开发 Server，不用关心 Host/Client 细节。

### 2.2 MCP 三大核心能力

| 能力 | 类型 | 作用 |
|------|------|------|
| **Tools** | 主动 | 执行操作（读文件、查库、发消息） |
| **Resources** | 被动 | 提供数据（按 URI 读取） |
| **Prompts** | 指导 | 提供提示模板 |

### 2.3 LLM 怎么决定用哪个工具？（5 步自动化流程）

```
1. 工具发现    Client 调 list_tools() 拿到所有工具的描述
2. 上下文构建  工具列表转成 LLM 能懂的格式塞进系统提示词
3. 模型推理    LLM 根据工具描述判断要不要调、调哪个
4. 工具执行    Client 通过 Server 执行所选工具
5. 结果整合    结果回传给 LLM，生成最终回答
```

⚠️ 工具描述写得好不好，直接决定 LLM 会不会用、怎么用。

### 2.4 MCP vs Function Calling（A/B 对比）

| 维度 | Function Calling | MCP |
|------|-----------------|-----|
| 本质 | LLM 的**核心能力**（模型内在智能） | **基础设施协议**（工程层面连接问题） |
| 工具定义 | 每个 LLM 一套格式（OpenAI 用 `parameters`，Claude 用 `input_schema`） | 统一标准，与模型无关 |
| 工具实现 | 自己写函数 + 处理各家响应格式 | 连接社区 Server，自动发现 |
| 切换模型 | 要重写大量适配代码 | 无需改动 |

**类比**：Function Calling 是你"会打电话"的技能（何时拨号、怎么沟通）；MCP 是全球统一的"电话通信标准"（任何电话都能拨通任何电话）。两者互补，不是竞争。

### 2.5 使用 MCP 客户端（核心 API）

```python
import asyncio
from hello_agents.protocols import MCPClient

async def main():
    # 方式1：连接社区文件系统服务器（npx 自动下载运行）
    client = MCPClient(["npx", "-y", "@modelcontextprotocol/server-filesystem", "."])
    # 方式2：连接自定义 Python MCP 服务器
    # client = MCPClient(["python", "my_mcp_server.py"])

    async with client:                    # async with 保证连接正确关闭
        tools = await client.list_tools()                 # 1. 发现工具
        print(f"可用工具: {[t['name'] for t in tools]}")
        result = await client.call_tool(                  # 2. 调用工具
            "read_file", {"path": "README.md"}
        )
        print(result)

asyncio.run(main())
```

还可以访问 Resources（`list_resources` / `read_resource`）和 Prompts（`list_prompts` / `get_prompt`）。

### 2.6 五种传输方式

| 传输方式 | 适用场景 |
|---------|---------|
| Memory | 单元测试、快速原型（`MCPTool()` 不传参即内置演示服务器） |
| Stdio | 本地开发、Python 脚本服务器（`server_command=[...]`） |
| HTTP | 生产环境、远程服务（用底层 MCPClient） |
| SSE | 实时通信、流式处理（`transport_type="sse"`） |
| StreamableHTTP | 双向流式 HTTP（`transport_type="streamable_http"`） |

### 2.7 在 Agent 中使用 MCP 工具（重点：自动展开机制）

```python
from hello_agents import SimpleAgent, HelloAgentsLLM
from hello_agents.tools import MCPTool

agent = SimpleAgent(name="助手", llm=HelloAgentsLLM())

# 无需配置，自动使用内置演示服务器
mcp_tool = MCPTool(name="calculator")
agent.add_tool(mcp_tool)
# ✅ MCP工具 'calculator' 已展开为 6 个独立工具：
#    calculator_add / subtract / multiply / divide / greet / get_system_info

response = agent.run("计算 25 乘以 16")
print(response)  # 25 乘以 16 的结果是 400
```

**自动展开原理**（这是 MCPTool 最巧的设计）：

```
用户代码:
  fs_tool = MCPTool(name="fs", server_command=[...])
  agent.add_tool(fs_tool)

内部发生:
  1. MCPTool 连接服务器，发现 14 个工具
  2. 为每个工具创建包装器: fs_read_text_file, fs_write_file, ...
  3. 注册到 Agent 的工具注册表

Agent 调用时:
  1. 识别需要 fs_read_text_file
  2. 生成参数: path=README.md
  3. 包装器转成 MCP 格式:
     {"action": "call_tool", "tool_name": "read_text_file",
      "arguments": {"path": "README.md"}}
  4. 调用 MCP 服务器，返回文件内容
```

⚠️ 挂多个 MCP 服务器时，每个 MCPTool 必须指定**不同的 name**——name 会作为前缀拼到展开工具名前，避免冲突。

### 2.8 实战：多 Agent 智能文档助手

两个 SimpleAgent 分工：GitHub搜索专家（挂 github MCP）+ 文档生成专家（挂 filesystem MCP），一个搜仓库、一个写 Markdown 报告——这就是"智能体+外部工具"的典型组合。

## 三、A2A 协议实战（智能体之间的对话）

### 3.1 设计动机：为什么不用中央协调器？

中央协调器（星型拓扑）三大问题：

| 问题 | 说明 |
|------|------|
| 单点故障 | 协调器挂了，系统全瘫 |
| 性能瓶颈 | 所有通信都过中心节点，并发受限 |
| 扩展困难 | 增删智能体要改中心逻辑 |

A2A 采用**点对点（P2P）网状拓扑**：每个智能体既是服务提供者也是消费者，能主动发起请求也能响应别人。

### 3.2 核心概念：Task 和 Artifact

A2A 与 MCP 最大的区别就是这两个抽象：
- **Task（任务）**：一次协作的最小单元，有标准生命周期：创建 → 协商 → 代理 → 执行中 → 完成/失败
- **Artifact（工件）**：任务产生的产出物

生命周期机制让智能体可以任务协商、进度跟踪、异常处理。

### 3.3 创建 A2A 智能体（skill 装饰器模式）

```python
from hello_agents.protocols import A2AServer

# 创建研究员 Agent 服务
researcher = A2AServer(
    name="researcher",
    description="负责搜索和分析资料的Agent",
    version="1.0.0"
)

# @skill 装饰器 = 注册一个技能，其他 Agent 可以远程调用
@researcher.skill("research")
def handle_research(text: str) -> str:
    return str({"topic": "AI医疗", "findings": "研究结果...", "sources": ["来源1"]})

# 后台启动服务
researcher.run(host="localhost", port=5000)
```

```python
# 客户端调用（另一台机器/另一个 Agent）
from hello_agents.protocols import A2AClient

client = A2AClient("http://localhost:5000")
response = client.execute_skill("research", "research AI在医疗领域的应用")
print(response.get('result'))  # {'topic': ..., 'findings': ..., 'sources': [...]}
```

### 3.4 多 Agent 流水线协作（研究员 → 撰写员 → 编辑）

三个 A2AServer 各起一个端口（5000/5001/5002），客户端依次 `execute_skill` 把上一步输出传给下一步，形成"研究 → 写稿 → 编辑"的内容生产线。这就是 A2A 版的任务分发与协作。

### 3.5 在 Agent 中使用 A2A 工具（A2ATool）

```python
from hello_agents import SimpleAgent, HelloAgentsLLM
from hello_agents.tools import A2ATool

coordinator = SimpleAgent(name="协调者", llm=HelloAgentsLLM())

# 把"另一个 Agent"包装成工具，塞进协调者
researcher_tool = A2ATool(
    name="researcher",
    description="研究员Agent，可以搜索和分析资料",
    agent_url="http://localhost:5000"
)
coordinator.add_tool(researcher_tool)

response = coordinator.run("请让研究员帮我研究AI在教育领域的应用")
```

**关键思维**：对协调者 Agent 来说，"调用另一个 Agent"和"调用一个工具"是同一件事——A2ATool 把 Agent 包装成了工具。

### 3.6 实战：智能客服系统

- 技术专家 / 销售顾问：两个 A2AServer（各带 `answer` 技能），分别跑在 6000/6001 端口
- 接待员：一个 SimpleAgent + 两个 A2ATool
- 流程：客户提问 → 接待员判断类型 → 调对应专家 → 汇总回答

## 四、ANP 协议实战（智能体的互联网）

### 4.1 要解决的三个问题

| 问题 | 说明 |
|------|------|
| 服务发现 | 新任务来了，怎么快速找到能干的智能体？ |
| 智能路由 | 多个都能干，选哪个（负载、成本）？ |
| 动态扩展 | 新智能体加入后如何被大家发现？ |

### 4.2 三步机制

```
1. 服务发现与匹配   通过公开发现服务（爬取各 Agent 的
                    .well-known/agent-descriptions 端点）按语义匹配

2. DID 身份验证     发起方用私钥对请求签名，接收方解析 DID 取公钥验签
                    → 去中心化的信任根基（没有中央 CA）

3. 标准化服务执行   双方按标准接口/数据格式交换
```

### 4.3 核心 API

```python
from hello_agents.protocols import ANPDiscovery, register_service, discover_service

discovery = ANPDiscovery()

# 注册服务（带负载、价格等元数据）
register_service(
    discovery=discovery,
    service_id="nlp_agent_1", service_name="NLP处理专家A", service_type="nlp",
    capabilities=["text_analysis", "sentiment_analysis", "ner"],
    endpoint="http://localhost:8001",
    metadata={"load": 0.3, "price": 0.01}
)

# 发现服务：按类型查，再选负载最低的
nlp_services = discover_service(discovery, service_type="nlp")
best = min(nlp_services, key=lambda s: s.metadata.get("load", 1.0))
```

### 4.4 实战：分布式任务调度 + 负载均衡

- 注册 10 个计算节点（随机 load / CPU / GPU 元数据）
- 任务调度 Agent（SimpleAgent + ANPTool）根据任务需求智能选节点
- 负载均衡示例：`min(servers, key=lambda s: s.metadata["load"])` 每次挑最闲的，模拟 10 个请求依次分配

## 七、关键知识点速查

### MCP（智能体的 USB-C）
- 三层架构：Host（界面）/ Client（通信）/ Server（功能），关注点分离
- 三大能力：Tools（主动执行）、Resources（被动数据）、Prompts（提示模板）
- 传输方式：Memory / Stdio / HTTP / SSE / StreamableHTTP，传输层无关
- **自动展开**：MCPTool 把服务器所有工具展开为独立工具，name 做前缀防冲突
- 与 Function Calling 互补：前者是模型能力，后者是基础设施协议

### A2A（智能体间的对话）
- P2P 网状拓扑，避免中央协调器的单点故障/瓶颈/难扩展
- 核心抽象：Task（任务+生命周期）、Artifact（工件）
- `@server.skill("name")` 注册技能，`client.execute_skill()` 远程调用
- A2ATool 把"另一个 Agent"变成协调者的工具

### ANP（智能体的互联网）
- 解决服务发现、智能路由、动态扩展
- 三步机制：发现匹配 → DID 身份验证（去中心化信任）→ 标准化执行
- `register_service` / `discover_service` + 负载元数据做负载均衡

### 选型口诀
- 访问外部服务 → MCP
- 多智能体协作 → A2A
- 大规模网络 → ANP
- 小规模团队协作用 A2A，大规模开放网络用 ANP，能组合使用

### 踩坑记录（重要）

1. **a2a-sdk 版本兼容**：hello-agents 0.2.2 按旧版 a2a-sdk API 写（`from a2a.client import A2AClient`）。最新 1.1.2 已把类改名为 `Client`，导致 `A2A_AVAILABLE=False`。**必须装 `a2a-sdk==0.3.26`**（最后保留旧 API 的版本）。装完后 `from hello_agents.protocols import A2AClient` 拿到的是 hello_agents 自己的 HTTP 封装（带 execute_skill / ask 方法），不是 a2a-sdk 原生的。

2. **A2A 服务器需要 Flask**：`A2AServer.run()` 用 Flask 提供 HTTP API，hello_agents 没把它列为依赖，要手动 `pip install flask`。

3. **ANPTool 的 LLM 调用需要明确格式**：把 ANPTool 挂进 SimpleAgent 后，如果不告诉 LLM 调用格式（`[TOOL_CALL:service_discovery:action=discover_services]`），LLM 会"要数据"而不是调工具。在 system_prompt 里写明调用方法后一次成功——再次验证了教程的观点：**工具描述/提示词质量直接决定 LLM 会不会用工具**。

4. **hello-agents 0.2.2 没有 `[protocol]` extra**：`pip install "hello-agents[protocol]==0.2.2"` 会警告 extra 不存在，但包本体 + fastmcp + mcp 会正常装上；A2A 依赖按上面 1、2 手动补即可。
