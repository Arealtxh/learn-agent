## 一、为什么要学这章？

### 第8章的局限

第8章给了你 **MemoryTool（记忆）** 和 **RAGTool（知识检索）**，但它们的问题是：

```
不加管理的做法：
  [记忆] "用户叫张三，Python开发者"      ← 都要进上下文
  [记忆] "张三已完成第4章"              ← 都要进上下文
  [记忆] "张三已完成第6章"              ← 都要进上下文
  [RAG]  "Python装饰器语法...200字"     ← 都要进上下文
  [历史] 过去20轮对话...                ← 都要进上下文

→ 上下文窗口爆了！而且真正相关的信息被淹没了
```

**"上下文是有限的稀缺资源，要像工程师一样去管理它"**

### 第9章的核心

| 问题 | 解决方案 |
|------|---------|
| 信息太多，放不进上下文窗口 | **Select** — 智能筛选最有价值的信息 |
| 所有信息混在一起，LLM分不清优先级 | **Structure** — 分区组织（Role/Task/Evidence/Context/Output） |
| 历史对话占满了上下文窗口 | **压缩** — 按需保留，必要时截断 |
| 长时程任务跨多天，需要记忆 | **NoteTool** — Markdown笔记，持久化项目管理 |

## 二、核心概念：从提示工程到上下文工程

### 提示工程 vs 上下文工程

```
提示工程 (Prompt Engineering)
  关注: "怎么写好提示词？"
  范围: 单次调用的输入
  类比: 学怎么写一封好邮件

上下文工程 (Context Engineering)
  关注: "什么信息应该进入上下文窗口？"
  范围: 整个交互生命周期
  类比: 学怎么管理一个项目的文档体系
```

### 上下文腐蚀 (Context Rot)

**发现**：即使模型支持 100K+ 上下文窗口，当上下文被塞满时，模型准确回忆信息的能力反而下降。

```
注意力预算 = 有限
每个新增 token 消耗一部分预算
→ 信息过多 = 注意力被摊薄
→ 相关性高的信息被噪声淹没
```

**结论**：不是「信息越多越好」，而是「信息越精越好」。

## 三、GSSC 流水线 — ContextBuilder

这是第9章最核心的工程成果。

```
                    ┌─────────────┐
                    │  ① GATHER   │  收集所有候选信息（不设限）
                    │  (收集)     │  系统指令 / 记忆 / RAG / 历史 / 笔记
                    └──────┬──────┘
                           ▼
                    ┌─────────────┐
                    │  ② SELECT   │  智能筛选：评分 + 排序 + 贪心选择
                    │  (筛选)     │  在 token 预算内选最优子集
                    └──────┬──────┘
                           ▼
                    ┌─────────────┐
                    │  ③ STRUCTURE│  结构化输出：分区组织上下文
                    │  (结构化)   │  [Role] [Task] [Evidence] [Context]
                    └──────┬──────┘
                           ▼
                    ┌─────────────┐
                    │  ④ COMPRESS │  超限时压缩或截断
                    │  (压缩)     │  保持结构完整性的前提下减量
                    └─────────────┘
```

### 各阶段详解

#### ① Gather（收集）

不限量收集所有可能的上下文来源：

```python
packets = []
packets.append(system_instructions)     # 系统指令（高优先级）
packets.extend(memory_results)          # 记忆系统
packets.extend(rag_results)             # 知识检索
packets.extend(note_results)            # 项目笔记
packets.extend(conversation_history)    # 对话历史（最近5条）
```

**设计要点**：每个数据源都是可选的，某个源失败不影响整体流程（try-except 包裹）。

#### ② Select（筛选）

最核心的阶段。两步：

**第一步：评分**

```python
综合分数 = 相关性权重 × 相关性 + 新近性权重 × 新近性
                   0.7                 0.3
```

- **相关性**（Jaccard 相似度）：内容和查询的关键词重叠比例
- **新近性**（指数衰减）：24小时内保持高分，之后衰减

**第二步：贪心选择**

```
1. 系统指令始终保留（高优先级）
2. 按分数从高到低排序
3. 依次加入，直到 token 预算用完为止
```

**为什么用贪心？** 因为「选最优子集」本身是个 NP 难问题（背包问题），贪心在工程上够用且快。

#### ③ Structure（结构化）

把散乱的信息包组织成清晰的分区：

```python
[Role & Policies]    ← 系统指令
[Task]               ← 用户当前问题
[Evidence]           ← RAG 检索的相关知识
[Notes]              ← 项目笔记（特别是 blocker）
[Context]            ← 对话历史 / 记忆
[Output]             ← 输出指引
```

**为什么分区比混在一起好？** LLM 能识别结构标记，知道「Evidence 区」的内容应该是事实依据，「Role 区」的内容是行为准则。

#### ④ Compress（压缩）

如果超限，按分区截断（而非"一刀切"）：

```python
# 先保系统指令，再保 Task，最后保 Evidence/Context
# 每个分区尽量完整保留，超限的分区才截断
```

## 四、NoteTool — 结构化笔记

### 和第8章 MemoryTool 的区别

| 维度 | MemoryTool（第8章） | NoteTool（第9章） |
|------|--------------------|-----------------|
| 格式 | JSON 记录（机器可读） | Markdown + YAML（人类可读） |
| 面向 | LLM 阅读 | 人类阅读 + LLM 阅读 |
| 用途 | 自动存储对话记忆 | 手动/半自动管理项目笔记 |
| 组织结构 | 扁平列表 | 分类 + 标签 + 元数据 |
| 版本控制 | 不友好 | 天然支持 Git |

### 笔记类型

| 类型 | 用途 | 优先级 |
|------|------|--------|
| `task_state` | 记录阶段性的任务进度 | 中 |
| `conclusion` | 重要结论和发现 | 中 |
| **`blocker`** | **阻塞问题**，需要优先解决 | **高** |
| `action` | 下一步行动计划 | 高 |
| `reference` | 参考资料 | 低 |
| `general` | 通用笔记 | 低 |

### 存储格式

每个笔记是一个独立的 `.md` 文件：

```markdown
---
title: 依赖版本冲突问题
type: blocker
tags: [dependency, urgent]
created_at: 2026-07-08T13:00:00
updated_at: 2026-07-08T13:00:00
---

## 问题描述
pandas 2.0 与 SQLAlchemy 1.4 不兼容...

## 影响范围
业务逻辑层3个模块
```

索引文件 `notes_index.json` 负责快速检索和元数据管理。

## 五、第8章 → 第9章的进化

### 数据流的演进

```
第7章: Agent → LLM（只有系统指令 + 当前输入）
第8章: Agent → Memory/RAG → LLM（加了记忆和知识）
第9章: Agent → ContextBuilder → LLM（加了智能筛选和结构化管理）

第9章的数据流:
  多个数据源 → GSSC 流水线 → 结构化上下文 → LLM
                     ↑
              ContextBuilder 自动管理
```

### 层次化上下文管理

```
第1层: TerminalTool（即时访问）
  → 按需探索文件系统，不预加载
  → 类比: 随时翻书，不把整本书记在脑子里

第2层: MemoryTool / NoteTool（会话记忆 + 项目笔记）
  → 自动/半自动保存，跨会话持久
  → 类比: 写笔记和日记

第3层: ContextBuilder（上下文管家）
  → 决定每一轮调用什么信息进上下文
  → 类比: 开会前准备材料清单，只带必需的
```

## 六、关键收获

### 思维转变

```
第7章之前: "怎么让 Agent 能做更多事情？"
第8章:     "怎么让 Agent 记住信息？"
第9章:     "怎么在有限窗口里放最有价值的信息？"
           "什么信息不进上下文，比进什么信息更重要"
```

### GSSC 核心设计原则

1. **容错** — 每个数据源独立，一个失败不影响整体
2. **可配置** — token 预算、权重、阈值都可调
3. **可观察** — 每个阶段都有日志，方便调优
4. **简单优先** — 贪心选择代替精确最优解

### Python 技巧

- **`dataclass`** — 用 `@dataclass` 定义数据结构，省去 `__init__`
- **`field(default_factory=...)`** — dataclass 中可变默认值的正确写法
- **Jaccard 相似度** — `交集/并集` 衡量两个文本集合的相似度
- **指数衰减** — `math.exp(-λ × t)` 模拟「近的信息更重要」
