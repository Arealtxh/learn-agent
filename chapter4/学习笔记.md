## 一、基础设施：`llm_client.py`

### 做了什么

封装对 DeepSeek (或任意 OpenAI 兼容 API) 的调用。所有范式都通过它跟大模型对话。

### 核心方法 `think(messages)`

```
┌─ messages ─┐     ┌─ DeepSeek API ─┐     ┌─ 完整回复文本 ─┐
│ user内容    │ ──→ │ stream=True     │ ──→ │ "Thought:...   │
│             │     │ 一个字一个字输出 │     │  Action:..."   │
└─────────────┘     └────────────────┘     └────────────────┘
```

### 关键代码

```python
response = self.client.chat.completions.create(
    model=self.model,
    messages=messages,
    temperature=temperature,   # =0, 让输出更确定
    stream=True,               # 流式输出
)
for chunk in response:
    collected.append(chunk.choices[0].delta.content)
return "".join(collected)
```

## 二、ReAct 范式 — 边想边做

### 核心思想

**Thought → Action → Observation 循环**。每一步先思考，再行动，观察结果后进入下一轮，直到得到答案。

类比：**侦探查案** — 发现线索 → 追查 → 发现新线索 → 再追查 → 最终破案。

### 架构

```
                问题
                  │
                  ▼
  ┌──────────────────────────────┐
  │  1. 拼 Prompt                │
  │    工具清单 + 问题 + 历史     │
  └──────────┬───────────────────┘
             ▼
  ┌──────────────────────────────┐  ┌──────────────────┐
  │  2. LLM 思考                 │  │ Prompt 约束格式：  │
  │  Thought: 分析问题            │  │ Thought: ...        │
  │  Action: 决定做什么           │  │ Action: Tool[...]  │
  └──────────┬───────────────────┘  │   或 Finish[...]   │
             ▼                      └──────────────────┘
  ┌──────────────────────────────┐
  │  3. 解析 Action              │
  │  "Search[华为最新手机]"       │
  │  → tool_name="Search"        │
  │  → tool_input="华为最新手机"  │
  └──────────┬───────────────────┘
             ▼
  ┌──────────────────────────────┐
  │  4. 执行工具                  │
  │  tool_fn(tool_input)         │
  │  → 调用 Tavily 搜索引擎       │
  └──────────┬───────────────────┘
             ▼
  ┌──────────────────────────────┐
  │  5. 记录 Observation 到历史   │
  │  history.append("Obs: ...")  │
  └──────────┬───────────────────┘
             │ ← 回到第1步，开始下一轮
             ▼
  ┌──────────────────────────────┐
  │  6. 如果 Action 是 Finish[]  │
  │  → 提取答案，结束循环 ✅      │
  └──────────────────────────────┘
```

## 三、Plan-and-Solve 范式 — 先规划后执行

### 核心思想

**两个阶段分离**：
1. **Plan 阶段**：一次性把问题分解成步骤列表
2. **Solve 阶段**：严格按照步骤逐一执行

类比：**建筑师盖楼** — 先画完整图纸，再按图纸施工。

### 架构

```
                   问题
                     │
                     ▼
        ┌────────────────────┐
        │  阶段1: 规划        │
        │  Planner.plan()    │
        │                    │
        │  输出:             │
        │  ["步骤1",         │
        │   "步骤2",         │
        │   "步骤3"]         │
        └────────┬───────────┘
                 ▼
        ┌────────────────────┐
        │  阶段2: 执行        │
        │  Executor.execute()│
        │                    │
        │  循环:             │
        │  步骤1 → 结果A     │
        │  步骤2 → 结果B     │
        │  步骤3 → 结果C ✅  │
        └────────────────────┘
```

### `planner.py` — 规划器

```
Planner
└── plan(question)
    1. 拼 Prompt（角色设定 + 格式要求）
    2. 调 LLM → 输出 "```python\n[...]\n```"
    3. 解析：
       a. split("```python")[1]   取代码块内容
       b. split("```")[0]         截到代码块结束
       c. ast.literal_eval()      转成 Python 列表
    4. 返回 [步骤1, 步骤2, ...]
```

**为什么用 `ast.literal_eval()` 不用 `eval()`？**

| | `eval()` | `ast.literal_eval()` |
|---|---|---|
| 能执行啥 | 任意 Python 代码 | 仅字面量 (str, int, list, dict) |
| 安全性 | ❌ 危险 | ✅ 安全 |
| 使用场景 | 绝不用于解析 LLM 输出 | ✅ 解析 LLM 输出的列表 |

### `executor.py` — 执行器

```
Executor
└── execute(question, plan)
    history = ""                # 状态管理：记录所有已完成步骤
    
    for 每步 in plan:
        1. 拼 Prompt:
           - 原始问题
           - 完整计划
           - 历史（之前步骤的输入+结果）
           - 当前步骤
        2. 调 LLM → 只输出当前步答案
        3. history += "步骤N: xxx\n结果: xxx\n"
    
    返回最后一步的结果
```

**Executor 的 Prompt 模板：**
```
# 原始问题: 水果店三天卖了多少苹果？
# 完整计划: ["计算周二", "计算周三", "计算总和"]
# 历史步骤与结果:
    步骤1: 计算周二... 结果: 30

# 当前步骤: 计算周三
# 请仅输出针对"当前步骤"的回答:
```

### `plan_and_solve_agent.py` — 组装

```python
class PlanAndSolveAgent:
    def __init__(self, llm):
        self.planner = Planner(llm)     # 组合规划器
        self.executor = Executor(llm)   # 组合执行器

    def run(self, question):
        plan = self.planner.plan(question)        # 阶段1
        answer = self.executor.execute(question, plan)  # 阶段2
        return answer
```

这个类本身不处理复杂逻辑，只负责调度 — 先规划、后执行。这叫**组合优于继承**。

### 运行效果

```
--- 开始处理问题 ---
问题: 周一15个，周二两倍，周三少5个，三天共卖出多少？

--- 正在生成计划 ---
LLM → ["计算周二：15*2",
        "计算周三：周二-5",
        "计算总和：15+周二+周三"]

--- 正在执行计划 ---
步骤1/3: 计算周二 → 输出: 30
步骤2/3: 计算周三 → 输出: 25
步骤3/3: 计算总和 → 输出: 70

最终答案: 70 ✅
```

## 四、Reflection 范式 — 执行→反思→优化

### 核心思想

通过 **事后自我校正循环** 迭代改进输出质量。类比：**作家写稿** — 写初稿 → 自己审阅修改 → 定稿。

类比另一种范式：
- ReAct = 侦探查案（边找线索边推理）
- Plan-and-Solve = 建筑师（先画图纸再盖楼）
- **Reflection = 作家（写初稿 → 审阅 → 修改 → 定稿）**

### 架构

```
                  ┌──────────────┐
                  │   初始执行    │ ← 初版代码
                  └──────┬───────┘
                         ▼
              ┌─────────────────────┐
              │   Memory.add_record │ ← 记入短期记忆
              └─────────────────────┘
                         ▼  循环开始
              ┌─────────────────────┐
              │  ① 反思 (Reflect)   │ ← LLM 扮演评审员
              │  → 挑代码毛病       │
              │  → 给出改进建议     │
              └──────────┬──────────┘
                         ▼
              ┌─────────────────────┐
              │  检查终止条件        │
              │  "无需改进" → 结束 ✅│
              │  否则 → 继续        │
              └──────────┬──────────┘
                         ▼
              ┌─────────────────────┐
              │  ② 优化 (Refine)    │ ← LLM 根据反馈改代码
              │  → 生成优化版       │
              └──────────┬──────────┘
                         │ ← 回到反思，继续下一轮
                         ▼
              ┌─────────────────────┐
              │  输出最终版本 ✅     │
              └─────────────────────┘
```

### `reflection_agent.py` — 核心实现

**三个 Prompt 角色：**

| Prompt | 角色 | 任务 |
|--------|------|------|
| `INITIAL_PROMPT` | 程序员 | 首次生成代码 |
| `REFLECT_PROMPT` | 评审员 | 挑代码毛病、给建议 |
| `REFINE_PROMPT` | 程序员 | 根据反馈改代码 |

**核心循环：**

```python
class ReflectionAgent:
    def __init__(self, llm, max_iterations=3):
        self.memory = Memory()
        self.max_iterations = max_iterations

    def run(task):
        # 1. 初始执行
        code = llm.think(INITIAL_PROMPT)
        memory.add_record("execution", code)

        # 2. 迭代循环
        for i in range(max_iterations):
            feedback = llm.think(REFLECT_PROMPT)  # 反思
            memory.add_record("reflection", feedback)

            if "无需改进" in feedback:             # 终止条件
                break

            code = llm.think(REFINE_PROMPT)        # 优化
            memory.add_record("execution", code)

        return memory.get_last_execution()         # 最终代码
```

### 终止条件

```python
if "无需改进" in feedback:
    break
```

当评审员认为代码在算法层面已最优时，输出"无需改进"，循环终止。否则继续迭代，最多 3 轮。

### 运行效果（预期）

```
初始代码: 试除法找素数 (O(n√n))
    ↓ 反思: "复杂度高，建议用埃拉托斯特尼筛法"
    ↓ 优化: 实现筛法 (O(n log log n))
    ↓ 反思: "代码已高效，无需改进"
    ↓ 完成 ✅
```

### Reflection 的成本收益

| | 说明 |
|---|---|
| **成本** | 每轮至少 2 次 LLM 调用（反思+优化），多轮叠加 |
| **延迟** | 串行迭代，总耗时显著增加 |
| **收益** | 从"合格"到"优秀"的质量跃迁 |
| **适合** | 代码生成、技术报告、复杂逻辑推理等高质量要求场景 |
| **不适合** | 实时响应、快速查询、"差不多就行"的场景 |

## 五、三大范式对比总结

| 维度 | ReAct | Plan-and-Solve | Reflection |
|------|-------|----------------|------------|
| **核心循环** | Thought→Action→Obs | Plan→Solve | Execute→Reflect→Refine |
| **类比** | 侦探查案 | 建筑师盖楼 | 作家写稿 |
| **阶段** | 单阶段循环 | 两阶段（规划+执行） | 三阶段（执行+反思+优化） |
| **决策时机** | 每步实时决策 | 一次性规划 | 迭代改进 |
| **外部工具** | ✅ 需要（搜索等） | ❌ 不需要（纯推理） | ❌ 不需要（纯推理） |
| **记忆需求** | 仅有历史列表 | 状态累加 | ✅ 需短期记忆模块 |
| **输出格式** | `Thought:\nAction:` | Plan: `[列表]` / 数值 | 代码/方案文本 |
| **LLM 调用次数** | 每步 1 次 | 规划 1 次 + 每步 1 次 | 1 + 每轮 2 次 |
| **适合场景** | 需要实时搜索的动态任务 | 结构化推理、多步计算 | 代码/报告等高质量要求 |
| **优点** | 灵活、适应变化 | 稳定、目标一致 | 质量跃迁、自我纠错 |
| **缺点** | 可能跑偏、每步开销 | 不灵活、Plan 错全废 | 成本高、延迟大 |

## 五、关键知识点速查

### Python 技巧

- **正则 `re.DOTALL`**：让 `.` 也能匹配换行符，适合跨行匹配
- **`ast.literal_eval()`**：安全地把字符串转成 Python 字面量
- **`re.match()` vs `re.search()`**：`match` 从开头匹配，`search` 搜索整个字符串
- **函数是一等公民**：可以把函数当变量存起来，需要时再调用

### Prompt 工程设计要点

1. **角色设定**：告诉 LLM 它是什么角色（规划专家/执行专家/评审员）
2. **格式约束**：指定精确的输出格式（方便代码解析）
3. **上下文注入**：把历史结果拼进 Prompt，形成记忆
4. **职责收窄**：每个 Prompt 只让 LLM 做一件事（比如 Executor 只答当前步）
5. **多角色协同**：Reflection 需要 3 个不同角色（程序员/评审员/优化者）的 Prompt 配合工作

### 常见陷阱

- LLM 不按格式输出 → 程序解析失败（需要 try/except 兜底）
- 上下文太长 → 超过模型 token 限制
- 工具调用失败 → 需要 graceful error handling
- Plan 不合理 → Solve 阶段会错到底（Plan-and-Solve 的固有弱点）
