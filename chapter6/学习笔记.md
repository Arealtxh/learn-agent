# 第一部分：第6章 — LangGraph（图的思维）

## 一、LangGraph 三要素：State, Node, Edge

### 和第4章的关系

| 第4章手写 | LangGraph |
|-----------|-----------|
| 你自己管循环 | 框架帮你遍历节点 |
| 手动拼 history 字符串 | State 自动维护 |
| 手动写 if/else 判断 | Edge 条件判断 |
| prompt 里写流程 | 图结构就是流程 |

### 1.1 State（状态）— 图的全局数据

```python
class CounterState(TypedDict):
    count: int           # 当前计数
    history: list[str]   # 记录每一步做了什么
```

State 是整个图的**全局共享数据**。所有节点都能读写 State 里的字段。对比第4章：你手写 `self.history = []` 来维护状态，现在 State 是强类型的（`int` / `list[str]`），IDE 会提示你类型错误。

### 1.2 Node（节点）— 每个节点就是一个函数

```python
def add_one_node(state: CounterState) -> dict:
    new_count = state["count"] + 1
    return {
        "count": new_count,
        "history": [*state["history"], f"第{new_count}次计数"],
    }
```

**约定：** 输入当前 State，返回要更新的字段（dict）。返回的内容会自动合并到 State 中。你不用管"什么时候更新 State"，框架帮你做。

对比第4章：每次调用 LLM 后你手动 `history += response`，现在只需要 `return {"history": [...]}`。

### 1.3 Edge（边）— 决定节点间的流向

**普通边：** 固定走 A → B
**条件边：** 根据 State 动态决定

```python
def route_after_add(state: CounterState) -> Literal["add_one", "__end__"]:
    if state["count"] >= 3:
        return "__end__"    # 结束
    else:
        return "add_one"    # 继续循环
```

对比第4章：你手写 `while True` + `if condition: break`，现在用条件边来表达"循环"和"终止"。

### 1.4 组装

```python
workflow = StateGraph(CounterState)      # 1. 创建图
workflow.add_node("add_one", fn)         # 2. 添加节点
workflow.add_edge(START, "add_one")      # 3. 入口
workflow.add_conditional_edges(          # 4. 条件边
    "add_one",
    route_after_add,
)
app = workflow.compile()                 # 5. 编译

# 运行：逐个节点执行，stream() 逐步输出
for step in app.stream(initial_state):
    ...
```

### 1.5 第4章范式 ↔ LangGraph 图拓扑的对应

| 第4章范式 | 图拓扑 | 特点 |
|-----------|--------|------|
| ReAct | **循环图**（Node 自指） | 同一个节点反复执行，条件边决定是否结束 |
| Plan-and-Solve | **链式图**（线性 Node 串） | 按固定顺序执行分支的每个节点 |
| Reflection | **循环图 + 条件分支** | 执行 → 反思 → 优化 → 再反思...满足条件才结束 |

**一句话：LangGraph 是通用的图执行引擎，第4章的三种范式只是图的三种拓扑结构。**

## 二、三步问答助手（LangGraph 实战）

### 2.1 数据流

```
  用户提问
     │
     ▼
  ┌──────────────┐
  │ understand   │  1. 分析用户问题，提取搜索关键词
  └──────┬───────┘
         ▼
  ┌──────────────┐
  │ search       │  2. 调用 Tavily 搜索
  └──────┬───────┘
         ▼
  ┌──────────────┐
  │ answer       │  3. 基于搜索结果生成回答
  └──────┬───────┘
         ▼
   最终答案 ✅
```

### 2.2 State 定义

```python
class SearchState(TypedDict):
    user_query: str         # ① 输入：用户原始问题
    search_query: str       # ② 传递：经过 LLM 优化的搜索词
    search_results: str     # ③ 传递：Tavily 返回的搜索结果
    final_answer: str       # ④ 输出：最终答案
    step: str               # ⑤ 标记：当前阶段（用于错误处理）
```

State 的每个字段 = 节点之间的**信息传递通道**。和队列式 `return` 不同，State 是全局共享的，任何节点都能读写任何字段。

### 2.3 错误处理

```python
def answer_node(state: SearchState) -> dict:
    if state["step"] == "search_failed":
        # 搜索失败 → 回退到 LLM 自身知识
        prompt = f"搜索暂时不可用，请基于你的知识回答：..."
    else:
        # 正常：基于搜索结果生成答案
        prompt = f"基于以下搜索结果回答..."
```

通过 `step` 字段做**状态感知**，让下游节点知道自己处于什么情况。这比第4章手写 try/except 更结构化。

### 2.4 第4章 vs 第6章 对比

| 维度 | 第4章手写 ReAct | 第6章 LangGraph |
|------|----------------|-----------------|
| 状态管理 | 手写 history 字符串 | State 全局自动维护 |
| 流程控制 | while + if/break | Edge 条件判断 |
| 可读性 | 逻辑和 IO 混在一起 | Node 职责清晰 |
| 扩展性 | 改流程要改循环逻辑 | 加 Node + 改 Edge 即可 |
| 学习成本 | 低（纯 Python） | 中（需学 LangGraph API） |

## 五、Layer 1：core/message.py — 消息系统

```python
class Message:
    def __init__(self, content, role, metadata=None):
        self.content = content           # 消息正文
        self.role = role                 # user/assistant/system/tool
        self.timestamp = datetime.now()  # 自动记录创建时间
        self.metadata = metadata or {}   # 可扩展字典

    def to_dict(self) -> dict:           # 转成 OpenAI API 格式
        return {"role": self.role, "content": self.content}
```

| 维度 | 第4章 | 第7章 |
|------|-------|-------|
| 格式 | 裸字典 `{"role": "user", "content": "..."}` | Message 类 |
| 扩展性 | 差（要改所有代码） | 好（加字段就行） |
| 类型安全 | 无 | `Literal["user", "assistant", "system", "tool"]` |
| 额外信息 | 需手写 | 自带 timestamp + metadata |

**Message 不是"把字典变成类就完了"——而是为后续所有功能提供了统一、可扩展的数据基础。**

## 七、Layer 3：core/agent.py — Agent 的"蓝图"（最重要的抽象）

### 7.1 什么是抽象基类（ABC）

```python
class Agent(ABC):
    @abstractmethod
    def run(self, input_text: str, **kwargs) -> str:
        pass  # 子类必须实现
```

ABC = Abstract Base Class。它不是"能直接用的类"，而是**规定子类长什么样的类**。

类比：**建筑蓝图说"要有门"，至于门是什么颜色、什么材质，蓝图不管。**

### 7.2 基类提供的公共能力

```python
class Agent(ABC):
    def __init__(self, name, llm, system_prompt=None):
        self._history: List[Message] = []   # 对话历史（所有子类共享）

    def _build_messages(self, input_text: str) -> list[dict]:
        """把 system prompt + 历史 + 当前输入拼成 API 格式"""
        messages = []
        if self.system_prompt:
            messages.append({"role": "system", "content": self.system_prompt})
        for msg in self._history:
            messages.append(msg.to_dict())
        messages.append({"role": "user", "content": input_text})
        return messages

    def add_message(self, message):     # 往历史追加
    def clear_history(self):            # 清空历史
    def get_history(self):              # 获取副本（保护性复制）
```

`_build_messages()` 是最重要的公共方法——第4章每个脚本都手写了这段逻辑。现在**写一次，所有子类复用**。

### 7.3 设计细节：保护性复制

```python
def get_history(self) -> List[Message]:
    return self._history.copy()  # 返回副本，防止外部误操作修改原始数据
```

## 八、Layer 4：agents/simple_agent.py — 第一个"活的"Agent

```python
class SimpleAgent(Agent):
    def run(self, input_text, **kwargs) -> str:
        messages = self._build_messages(input_text)    # 1. 拼 prompt（复用基类）
        response = self.llm.invoke(messages, **kwargs) # 2. 调 LLM
        self.add_message(Message(input_text, "user"))         # 3. 记历史
        self.add_message(Message(response, "assistant"))      # 3. 记历史
        return response
```

**4 行核心逻辑。** 对比第4章你要写 ~50 行才能实现同样功能。

`super().__init__(...)` — 子类必须手动调用父类构造函数，否则不会自动拥有 `name`、`llm`、`system_prompt`、`_history` 这些属性。

## 九、Layer 5：agents/react_agent.py — ReAct + ToolRegistry

### 9.1 ToolRegistry — 工具注册中心

```python
class ToolRegistry:
    def __init__(self):
        self._tools: Dict[str, Dict] = {}

    def register(self, name, description, fn):
        self._tools[name] = {"description": description, "fn": fn}

    def get(self, name):
        tool = self._tools.get(name)
        return tool["fn"] if tool else None

    def get_tool_descriptions(self) -> str:
        """自动生成给 LLM 看的工具描述文本"""
        lines = ["可用工具："]
        for name, info in self._tools.items():
            lines.append(f"  - {name}: {info['description']}")
        lines.append("使用格式: 工具名[参数]   例如: Search[今日新闻]")
        return "\n".join(lines)
```

对比第4章的 `tool_executor.py`：

| 维度 | 第4章 | 第7章 |
|------|-------|-------|
| 工具存储 | 硬编码字典 | ToolRegistry 类 |
| 加新工具 | 改代码 | `tools.register()` |
| 描述文本 | 手写进 prompt | `get_tool_descriptions()` 自动生成 |

### 9.2 ReActAgent — ReAct 循环的框架化

```python
class ReActAgent(Agent):
    def __init__(self, name, llm, system_prompt=None, tool_registry=None, max_steps=5):
        super().__init__(name, llm, system_prompt)
        self.tools = tool_registry or ToolRegistry()
        self.max_steps = max_steps
```

**关键设计决策：为什么 ReAct 循环内部用 history 字符串，而不是 Message 历史？**

因为 ReAct 循环内的 Thought/Action/Observation 是"一次任务的中间步骤"，不是"对话历史"。如果每次 Thought 都加到 `self._history` 里，对话历史会被吃满。所以 ReAct 用独立的 `history` 字符串，只在结束时把最终答案保存到 `self._history`。

```
                        ┌──────────── 本轮 ReAct ────────────┐
                        │                                     │
history = ""  ──→ Thought: 需要搜索  ←── LLM 输出             │
                 Action: Search[xxx]  ←── LLM 输出            │
                        │                                     │
                        ▼ ←── 执行工具，得到 Observation       │
                                                                 
history += "Thought: ...\nAction: ...\nObservation: ...\n"  ──┘
                        │
                        ▼ ──→ 进入下一轮 / Finish
```

### 9.3 ReAct 循环的解析逻辑

```python
# 解析 Thought
re.search(r"Thought:\s*(.*?)(?=\nAction:|$)", response, re.DOTALL)

# 解析 Action
re.search(r"Action:\s*(.*?)$", response, re.MULTILINE)

# 检查 Finish
re.match(r"Finish\[(.*)\]", action_text)

# 解析工具调用
re.match(r"(\w+)\[(.*)\]", action_text)    # Search[xxx] → ("Search", "xxx")
```

每一步都用正则匹配，匹配失败就记录错误到 history，让 LLM 在下一轮自行修正。这就是 ReAct 范式"容错性"的实现——不完美就重来。

### 9.4 SimpleAgent vs ReActAgent

| 维度 | SimpleAgent | ReActAgent |
|------|-------------|------------|
| 继承自 | Agent | Agent |
| 工具 | 无 | ToolRegistry |
| 循环 | 一次调用 | 多轮 ReAct 循环 |
| 历史保存时机 | 每次 run 都保存 | 只在 Finish 或超时保存 |
| 使用场景 | 纯聊天 | 需要搜索/计算的复杂任务 |

## 十二、关键知识点速查

### Python 面向对象

- **抽象基类 (ABC)**：定义接口规范，子类必须实现 `@abstractmethod`
- **`super().__init__()`**：子类构造函数必须手动调用父类构造函数
- **保护性复制**：`return self._list.copy()` 防止外部误修改内部数据
- **组合优于继承**：`self.planner = Planner(llm)` 而不是 `class MyAgent(Planner)`

### 框架设计原则

- **单向依赖**：底层不知道上层存在，上层可以复用底层
- **封装变化**：把"容易变的"（工具实现）和"不变的"（Agent 流程）分开
- **依赖注入**：`llm` 和 `tools` 通过构造函数传入，不是内部 new 出来的
- **`__init__.py`** = 给使用者看的"菜单"——隐藏内部目录结构

### LangGraph 要点

- **State** = 图的全局共享数据（TypedDict）
- **Node** = 一个函数（State → dict）
- **Edge** = 固定指向（add_edge）或条件指向（add_conditional_edges）
- `add_conditional_edges` 返回 `"__end__"` 代表 `END`
- `stream()` 逐步输出每个节点后的 State 快照
- LangChain 和 LangGraph 是两回事：LangChain = LLM 工具链，LangGraph = 图执行引擎

### 框架 vs 库 vs 工具

- **工具**：帮你完成一件事（比如 Tavily 搜索）
- **库**：给你一些可调用的函数（比如 LangChain）
- **框架**：规定了"你怎么写代码"（比如 LangGraph、HelloAgents）
- 框架的核心是**控制反转**——不是你的代码调用框架，而是框架调用你的代码（Node 函数）
